# 数模 Agent：参考仓库评估与架构建议

评估日期：2026-09-06。本文是设计建议，不是已接受 ADR；没有将参考代码迁入 Daedalus 或 Theia。

## 结论

采用 math-model 的领域流程，借鉴 Claude Science 的执行工作台和结果追溯模式，在 Daedalus / Theia 中独立实现。优先完成“题目和数据 → 建模 → 真实计算 → 检验 → 图表 → 论文”的可恢复闭环。

特别需要改变的两项旧逻辑：

1. comp-code 的恢复提示以 RESULTS.md 大于 1KB 判断“完整”，不足以证明步骤成功。应使用输入摘要、代码摘要、环境版本、结构化输出和验收结果判断能否复用。
2. workflow_engine.py 的检查点说明包含“超时自动确认继续”。新设计应区分可自动继续的普通阶段与必须等用户决策的检查点；后者超时应保持等待或显式过期。

技能材料可作为候选内容逐项整理，来源、引用与模板依赖随包登记；本次未对所有技能的每一项外部依赖做逐项验证，也未宣布整包可直接投产。

## 3. 可纳入 Theia 的设计

| 产品界面 | 参考 | 新产品中的作用 |
|---|---|---|
| 项目入口与创建向导 | math-model 前端的 /new、赛题上传、模板选择 | 输入题目、附件、比赛类型、目标和预算；模板步骤来自后端契约 |
| 阶段时间线与交互区 | math-model 的 workflow 页面、检查点、实时日志 | 用户知道正在做什么、为何等待、失败在哪里；支持反馈、重试和取消 |
| 工作区与编辑预览 | math-model 的 editor/artifact 页面；Claude Science 的多类型 preview 模式 | 先支持 Markdown/公式、代码、CSV、图片和 PDF，再考虑 Notebook |
| 结果详情与来源面板 | Claude Science 的 provenance/execution log 模式 | 从图表或论文数字反查输入、代码、执行和版本；展示是否过期或未验证 |
| 修改审阅 | Claude Science 的文本/LaTeX diff 和计划审批模式 | 展示 AI 提议与当前版本差异；接受时携带版本号，避免覆盖用户新修改 |
| 设置与环境状态 | 两仓库的执行器/环境配置设计 | 展示可用执行后端、工具链和缺失依赖；密钥保存与执行策略留在后端 |

建议布局：左侧项目/任务与产物导航，中间任务交流和阶段进度，右侧按需打开文件、图表或来源详情。独立设计组件、视觉与文案。

math-model 的 dist/assets/index-DM6e8jaR.js 可读到工作流、文件、编辑器、设置路由及 WebSocket 指数退避重连；没有原始 React/TypeScript 模块或开发构建链，适合提取需求后重建。

Claude Science 的部分 src/frontend 模块以注入 React/query/API 等依赖的 factory 存在，仍与 canonical runtime 组合运行；不能把它们当成脱离原产品即可直接使用的 UI 组件库。

## 4. 建议的独立架构

```text
Theia：任务工作台 / 检查点 / 产物预览 / 编辑审阅 / 来源展示
                         │
                版本化 HTTP + 事件契约
                         │
Daedalus：任务应用服务 → 状态机与调度 → 技能和执行器适配
                │                 │
           状态与事件库       隔离工作区 / Python / 文档编译
                └──── 产物版本、执行记录和结果验证 ────┘
```

建议初期选型为 Theia 的 React + TypeScript + Vite，Daedalus 的 Python + FastAPI + SQLite，适合现有数模材料及 Python 计算生态。这是候选方案，不是仓库既定决定。若后端主服务最终选 Node/TypeScript，也应把计算执行通过独立进程协议隔离，不必把模型算法重写成 JavaScript。

先采用模块化单体加独立执行进程，不急于拆微服务或建设通用多 Agent 平台。业务执行状态和权限必须由后端决定，前端只发命令并展示服务端状态。

## 5. 应先确定的接口契约草案

以下概念与字段是为数模项目提出的独立草案，不搬用参考产品整套路由或 DDL。

| 概念 | 最小内容 |
|---|---|
| 项目 | 标识、题目、附件集合、目标与预算 |
| 任务运行 | 标识、模板版本、输入版本、状态、当前阶段、状态版本号 |
| 阶段尝试 | 阶段标识、尝试编号、执行器、开始/结束、错误与验证结果 |
| 产物版本 | 标识、类型、内容摘要、创建它的执行、输入版本、存储引用 |
| 检查点 | 标识、关联阶段/产物版本、待决策内容、允许动作、当前状态 |
| 执行记录 | 参数摘要、代码摘要、环境、随机种子、输出、退出状态及资源用量 |
| 事件信封 | 契约版本、唯一事件 ID、任务 ID、递增序号、事件类型、载荷 |

最低协议语义：

- 创建/重试/确认等写操作带幂等键，状态修改带期望版本。
- 事件流允许按序号补读；先取快照再接增量，重复事件去重。WebSocket 重连本身不等于状态恢复。
- 失败和取消有结构化结果；取消终止执行进程树，并避免晚到结果把任务改回成功。
- 产物采用稳定 ID 与版本，前端不依赖本地绝对路径。
- 编辑保存检查基准版本，冲突时返回差异而非静默覆盖。
- 契约作为独立版本化发布物由双方钉住；跨仓库版本一致性需设计可只读验证的发布元数据，不依靠门禁读取对侧源码。

## 6. 哪些部分不进入当前设计

- 不整体迁入反编译 Python、生产 bundle、恢复二进制、第三方 UI 资源或完整数据库/路由目录。
- 不继承 math-model 的 FastAPI 托管前端 dist 做法：Daedalus 的现行边界不容纳前端材料。前端静态部署与 API 部署可由外层部署配置组合。
- 不优先接入 Electron/Swift 桌面壳、内嵌数 GiB 运行时、云存储、多组织、生物学可视化、远程 GPU 或大型 connector 目录。
- 不把 Claude Science 的差分验证工具整体带入新仓库：它们用于验证与发布件等价；新系统需要验证自己的需求与契约。
- 不直接导入 src/**：该仓库当前公开消费面仍为空。可参考架构知识并独立实现；本次用户请求是设计评估，不需要等待代码导入授权才完成。

## 7. 落地顺序与验收

1. **契约和模板**：明确任务、阶段、检查点、产物和事件；形成候选 ADR；定义一条中文数模最小模板。验收：双方从同一契约生成/校验模型。
2. **真实计算闭环**：题目/数据上传 → 分析 → 建模 → Python 执行 → 结果验证 → 前端查看结果。验收：使用已知答案的小型优化或回归题，核对计算结果及输入来源；失败不能被当作成功。
3. **可靠性与追溯**：补全版本、执行记录、断线补读、重启恢复、取消和检查点。验收：中断后恢复不重复执行已完成副作用，重复确认不会重复推进。
4. **论文交付**：图表读取已验证数据，论文数字关联结果版本，LaTeX 编译返回诊断。验收：改动数据后相关产物标为过期；生成可下载 PDF，并能追溯其中关键图表。
5. **扩展**：再加入不同竞赛模板、文献能力、LLM 复核、更多执行器和远程计算。

仓库治理同步项：源码扩展名检查补入 Python/TypeScript；长行策略覆盖新源码根；内容 manifest 按既有生成命令更新；增加独立业务测试。架构/目录相关 ADR 的接受状态依现行规范由所有者填写。两个现有基座的 GitHub Actions 最新运行此前因账号计费条件未启动，需恢复 CI 自动执行。
