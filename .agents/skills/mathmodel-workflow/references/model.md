# 基线与改进

## baseline

在 baseline.md 定义最简单有用模型的变量、单位、公式、约束和适用条件。
写实际脚本，用 run 执行并记录代码、数据、参数文件为 --input，结果为 --output。
明确基线的可行性、误差及局限。计算题不能只提交数学描述；理论题保留推导、前提和边界检查。
complete baseline 同时登记说明、代码和结果，并通过 --execution 指向本阶段实际执行。

## improve

针对基线的具体不足提出改进假设，在 model.md 先写实验计划，再运行。
比较使用相同数据/预算/指标；保留不成功实验，不按结果临时放宽阈值。
优化记录可行性、目标、求解状态与 gap；超时的可行解不称全局最优。
仿真记录种子、重复次数和不确定性；评价模型检查权重扰动和排序稳定性。
改进无效可以选择基线，说明原因。无需为满足数量而发明多个候选。

基线足够或剩余预算不适合改进时：skip --stage improve --reason "具体依据"。
其他阶段不能跳过。重新计算已有阶段前 reopen，使用新输出文件名，旧摘要和内容快照可追溯。

## 从小问到模型、代码和结果

按 [模型与实现模板](../assets/worksheets/model-plan.md) 在 baseline.md 或 model.md 中逐问记录；简单题可合并成几段。沿用 problem.md 的 Q 编号，写出模型对应哪些原题要求。

选择模型时比较数据适配性、参数能否确定、解释能力和计算成本，而不是只列算法名称。确有多种合理选择时解释取舍；不要求每题凑齐多种方法。偏离分析阶段建议时记录原因，例如样本量不足、假设不成立或求解规模不合适。

每个模型写清：变量与量纲、参数来源、假设依据、目标/方程与约束、推导关键步骤、可行性和极限情形。理论题给出命题前提与证明结构；统计题分开拟合、调参、评价；评价题解释指标方向及权重依据。

编程前把每问落实到脚本/函数、输入字段、参数、求解器与容差、结果文件/字段和验证办法。数学模型使用连续量但代码离散化、理想模型忽略因素但代码加入截断等差异，必须注明及解释影响。结果文件存在不等于实现正确。

按依赖顺序求解，独立的小问不必人为串联。每问先执行、检查，再把有效输出用于下游。共享参数统一定义；记录 solver status、失败与近似，不把不收敛结果当有效结论。耗时是否合理由问题规模和预算判断，不设置通用的“三分钟重写”规则。

保存绘图和核验真正需要的数据：例如逐样本预测、残差、参数扫描、各次仿真结果或约束残差，而不只保存最终均值。诊断图可以在计算阶段生成；供论文使用的图仍在 figures 阶段登记和审查。

敏感性范围由参数来源和现实可能性确定，关注会改变决策的因素；不机械采用统一百分比。仿真比较可以使用配对随机输入降低比较方差，但要解释配对依据。不得为了让改进方法获胜筛选种子、删样本或调整合成数据。
